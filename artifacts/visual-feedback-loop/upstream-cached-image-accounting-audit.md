# Upstream cached-image resource accounting audit

## Decision — PARTIAL

Source supports a **distinct active Vision-work accounting boundary**, not a requirement that every historical patch be materialized again. Local `encode_new()` already implements the relevant skip; no second Vision path is needed. However, **this audit does not justify changing the enforced 36,864 all-occurrence guard**. Two qualifications prevent an end-to-end CONFIRMED conclusion:

1. At the pinned official revision the cache-aware processor API exists, but the inspected ordinary engine caller does **not pass its cached-token frontier**. It calls `add(request_id, multi_modal_data)` and therefore supplies the default zero. The scheduler handoff must not be described as a demonstrated working cache-aware pipeline at this revision.
2. The local patch guard also indirectly bounds all-history metadata/occurrence growth and the size of requests allowed to reach paired restoration. Removing that charge admits a different memory envelope, including paired snapshots and all-history metadata. Finite independent bounds exist, but their resulting peak memory is not qualified by source inspection or Q1/Q2.

The exact candidate boundary is **after successful immutable Target/DSpark acquisition, identity/whole-span validation and historical-frontier coverage in `ProductionScheduler._schedule_waiting`, before `_start` → `_encode_new_images` → `MultimodalInput.encode_new` allocates normalized patches**. Only whole images outside that validated frontier would belong to an active-work patch sum. This is a future investigation boundary, not authorization, a changed capability or an implementation plan.

### Material official handoff finding

`deepinfer/engine/llm_engine.py:543–551` expands the prompt before constructing the sequence. Its `_enqueue` at **620–625** calls `scheduler.add_sequence(s)` and then **`self.multi_modal_processor.add(request_id, multi_modal_data)`**, without a third argument. `MultimodalProcessor.add` at **248** defaults `num_cached_tokens=0`; `_compute_and_strip_cached_images` immediately returns for zero at **222–223**. Thus this caller does not activate cached-prefix stripping/substitution.

Direct scheduler inspection does not fill that gap: `csrc/engine/scheduler.hpp:135–142` reserves/queues the sequence, not a Python callback supplying a frontier. `_schedule_prefill:350–460` checks `schedulable` before prefill/cache/block decisions, and `set_schedulable:1054–1058` only sets a flag. Processor `fetch`, `ve/multimodal_processor.py:287–315`, updates processed metadata then calls that flag setter. `llm_engine.py:940–942` pumps fetch/aborts. Repository-wide source search found no other production call to this processor's `add` passing cached tokens.

Consequently distinguish **implemented conditional cache-aware mechanism** from **ordinary engine wiring**. The code proves how supplied cache coverage affects image preparation; it does not prove the ordinary pinned engine supplies it. This also qualifies the stronger summary wording in the current implementation plan without editing historical evidence.

## 4. Official mechanism and alignment

When a nonzero frontier is supplied, official processing:

1. Finds only consecutive fully covered image spans; a boundary inside an image leaves its **entire payload uncached** (`multimodal_processor.py:234–245`). No fractional patch discount.
2. Sets cached `ImageInput.binary=None` before IPC, not a request-wide promise that all source/security costs are zero.
3. `_split_cached_prefix` consumes complete text/image segments only. A partial text segment stays; an image is never split into a fake cached fragment. Equal-length `TextLengthInput` preserves downstream absolute token indexing (`deepseek_vl.py:41–76`). Engine token IDs themselves are not replaced by dummy text.
4. Converts only remaining image segments. Original full `image_spans` remain; cached rows are prepended as zero crops, zero real sizes when fresh raw data exists, and zero cumulative patch increments (`deepseek_vl.py:127–203`). Full token-type metadata still has prompt length; dummy cached prefix rows are never required as new image embeddings.
5. Chunks token metadata in absolute prompt coordinates; selects overlapping image indices with span starts/ends, slices packed raw bytes and patch positional metadata with cumulative offsets, filters zero crop rows. `total_image_patches` sums **active nonzero crops in this chunk/batch**, not history (`prepare_tensor_input_vl.py:31–172`). An image overlapping an active chunk is included whole, not prorated by token overlap. All-cached work produces no raw payload/cu-ViT work; `get_input_embeddings` skips the tuner if `images_raw is None`.

The allocation consumer makes the boundary concrete: `model_executor/layers/tilelang_ops/image_embed_ops.py:43–83`, `rgb_pad_to_patches`, allocates `torch.empty((total_patches, 3, patch_size, patch_size), dtype=torch.bfloat16)`. Thus the active sum actually sizes the normalized patch tensor; it is not merely logging. `ve/processor/mm_processor.py:23–30` routes only remaining segments to their modality processor; `ve/processor/text_processor.py:10–13` creates only length-sized zero token-type metadata for dummy text. Cached substitution still has metadata costs.

This is a tensor sizing/work mechanism, not evidence of an upstream hard admission ceiling equivalent to 36,864, nor of universal cache recovery. Official code does not establish local Target/DSpark numerical integrity. Locally `encode_new` already supplies the relevant fresh-only behavior with absolute sparse merge (`multimodal.py:126–132`), while deliberately **rejecting** partial-image frontiers rather than adopting official reprocessing semantics.

## 5. What the 36,864 guard protects

**Direct current effect:** bounds aggregate planned grids before the request can enter the executable worker. At full miss it bounds all images that would be normalized/encoded. At a valid hit it conservatively bounds more than the actual Vision work. CPU normalization is float32 over padded RGB (`processing.py:110–119`); MLX pixels, encoder intermediates and retained projected rows add costs. The scalar patch count is a conservative workload proxy, not a bound in bytes on every allocation or a guarantee against OOM.

**Indirect effect:** caps occurrence/kinds/span metadata and requests reaching restoration even when source pixels are small (grid planning can upscale small sources). Moving only the patch charge later would remove this indirect cap. Remaining byte/pixel/context/per-image limits still bound earlier work; no source path found allocates full-history normalized patches before lookup. Nevertheless context-bounded metadata at up to the implemented envelope can be much larger than under today's guard. Some temporary arrays are allocated before their later bounds are checked. Source proves finiteness, not acceptable peaks, latency or denial-of-service tolerance.

**Before cache restoration:** full body/JSON/Recipe/source bytes, all-container decode/validation, hashes, geometry/kinds, expanded token lists/tuples, identities. The 36,864 check itself follows validation for the image that crosses it; it is not the primary protection for malicious encoded containers. Keep byte/pixel/container/context checks early.

**After lookup/restoration:** actual new-image normalization/patching/encoding and cumulative fresh embedding rows, suffix prefill/KV growth, prompt/final paired capture, settlement/publication. Restoration itself precedes fresh work and may materialize/share/copy significant state. Existing aggregate-patch policy rejects some large-history requests before that restoration. Context/output and finite checkpoint count do not alone quantify active-plus-retained snapshot peaks.

Thus historical patches and fresh patches **need not share a Vision-tensor-work count by the allocation semantics**. They must still share applicable all-history transport/validation/metadata/context/state budgets. Changing the former does not erase the latter or prove the present patch guard redundant as a coarse overall resource safeguard. No generic `runtime/resource_admission.py` binding check substitutes for this production analysis: `encode_new`'s default binding validation is bypassed only when the production pinned `span_encoder` adapter is supplied; that adapter enforces pinned Model/MTP binding (`production_mtp.py:312–325`).

## 7. Safety invariants and remaining uncertainties

Unchanged invariants:

- Validate every supplied container/identity/order and complete expanded prompt regardless of a potential hit; retain per-image, aggregate bytes/pixels, context plus output and terminal-text checks.
- Cache skip requires **actual** complete paired restoration with exact execution identity/tokens/image identities. Historical flags impose coverage, not permission to invent a hit. No second lookup authority or cache manager.
- `validate_pair` (`paired_checkpoint.py:29–47`) requires 40 Target layers, seven cache slots with committed layouts/tails, three physical DSpark rings (capacity 128) at the same frontier and singleton dimensions. Capture/restore validates both; no Target-only restoration or intersecting-image frontier.
- No hidden history replay/re-encoding, recurrent trim, stale-pair substitution, offload, compaction or retry of tool effects. Logical retained sessions require their exact canonical pair, not an ordinary shorter hit.
- Publish only immutable settled canonical paired state, retire executable ownership, release request-owned image work on cancellation/failure; no cache publication after failed native mutation.

Unresolved: official nonzero-frontier production handoff at the pinned revision; numerical/semantic behavior under that handoff; local metadata/body/queue amplification at the newly reachable history envelope; restore/capture copy-on-write and allocator/wired peak coexistence with active Vision; cancellation/failure cleanup under those peaks; installed-payload behavior. Existing finite count/context bounds are not measured memory guarantees. This audit neither challenges Q1's seven-image admission result nor turns it into a new universal capacity.

## 8. Minimum next gate (separate approval required)

Only a focused **boundary-evidence gate** is justified, not an implementation or broader offload/compaction campaign:

1. Resolve the official caller discrepancy at this exact revision (or explicitly review a separately pinned correction); do not silently ascribe a nonzero frontier to the current call.
2. Independently establish explicit acceptable bounds for all-history metadata/occurrences and paired restoration/capture coexistence if their indirect patch cap were removed. Include tiny-source/upscaled images, bounded body with many occurrences and queued request retention. No numerical threshold is selected here.
3. Before any production relaxation is approved, require focused model-free admission/lifecycle evidence and independently authorized real installed MLX verification: exact cached-prefix numerical/identity equivalence, all case-matrix failures, unchanged fresh/miss budget, measured peak resident/allocator/wired memory, and failure/cancellation settlement/cleanup. Historical Q1/Q2 receipts do not qualify altered admission.

If those gates justify a change, the minimum conceptual difference is **separate early all-history validation/metadata bounds from an active planned-patch admission immediately after validated paired lookup and before fresh Vision allocation**, using the existing `encode_new` path and retaining 36,864 as the active-work candidate ceiling, not raising it. Account explicitly for restoration occurring earlier. No guard is changed by this report; no replay/recovery or scheduler/cache redesign is proposed.
