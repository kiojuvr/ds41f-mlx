# Release qualification

This page owns **release-proof interpretation and selected-payload review**, not
an at-HEAD QUALIFIED badge or a historical launch recipe. [Capabilities](capabilities.md)
owns implemented support; [qualification](qualification.md) owns proof levels;
[operations](operations.md) owns deployment; [promotion strategy](reference-release-and-promotion-strategy.md)
owns source/reference/delivery authority. Compilation publishes no release.

## Historical release scope and current operation

`DS41F_TEXT_RUNTIME_RELEASE_QUALIFIED` is the original scoped local OFF text
release designation, not a universal project-complete claim. Earlier M20/M21/M22
and later M44 evidence binds its exact dependency/runtime/client/payload inputs.
The [original release edition](archive/editorial-baseline/release-qualification.md.txt)
retains the full PASS matrix, upstream revisions, commands, paths, performance
class and old exclusions. Do not reinterpret M25's MTP rejection or that OFF-only
release scope as the current repository's capability policy.

Explicit ordinary MTP, bounded OFF images, applications and generation controls
have their own later evidence. Singleton M54R/M55R release approval remains bounded;
no profile inherits another's API, persistence, images, sampling or release proof.
General-runtime production release is still incomplete. The old `ds41f-runtime`
directory is unused generation, not deployment or accepted release history.

## Development qualification versus release promotion

Development may accumulate qualified changes without publishing/projection after
each milestone. Validate affected contracts and applicable reference/model/state/
resource boundaries. Full R1 at an appropriate stable boundary and explicit release
review are separate decisions, not triggered by every surface edit.

A selected release must identify exact source/package/reference/dependency/assets,
admitted profiles and actual acceptance. Future source projection follows the
existing deterministic mechanism and independent setup/receipt rules. Historical
M43/M44 receipts remain facts about their payloads; they neither certify later
HEAD nor require regenerated receipts whenever documentation changes.

## Supported scope

The review starts from **the selected payload's declared scope**, not everything
implemented in development or parsed upstream. State profile, checkpoint/platform,
protocols, context/output policy, execution owner, tools/effects, session/concurrency,
network, persistence and exclusions. Resolve capability versus defaults versus
resource/security policy explicitly.

Current comparison and owning evidence live in capabilities. A text-core, image-core,
HTTP/client, installed-admission or singleton PASS cannot silently become a broader
release claim. This page supplies review rules, not a newly completed scope matrix.

## Public contract closure

Use current [OFF API](api.md), [ordinary admission](ordinary-api-boundary.md),
[ordinary MTP](mtp-production-serving.md) and
[logical sessions](production-sessions.md) for selected endpoint semantics.
OFF now has demand-driven live streaming; the old completed-turn-only description
is historical. Admission rejection and runtime fault/poison disposition are distinct;
not every execution error means all consumed tokens rolled back.

A review must address truthful readiness, parameter support/rejection, exact
continuation, stale/foreign identity refusal, ambiguous delivery, cancellation,
resource cleanup and client effect permission. HTTP success or SSE delivery is not
canonical history, native restore, client ACK or exactly-once external effects.

## Historical checkout startup (not current operator instructions)

Earlier source/provenance launches, donor-path configuration and old environment
commands are preserved in the edition. They must not replace installed non-editable
admission or become advice to refresh local seals. Use operations and
[runtime admission](runtime-admission.md) for exact executable/semantic assets,
separate host compatibility and graceful shutdown. Process alive is not model ready;
forced kill is not successful native retirement or recovered sessions.

## Regression matrix

At a release checkpoint maintain a concise **scope-specific assessment**, with
owner, exact input identity, observable predicate, result/exclusions and evidence.
Typical rows include supported independent/stateful text, EOS/length, tools/results,
JSON/SSE, continuation, cancellation/ambiguous delivery, negative admission,
resource cleanup and persistence/restore **only where supported**.

The historical matrix remains in the edition. A recorded PASS stays there; pending
or changed scope needs its own disposition, not copied PASS cells or a full-suite
count used as release proof. Representative long-context evidence is not every
maximum HTTP/agent/output endurance workload. Unknown or failed gates remain explicit.

## Invariants retained

Official checkpoint/recipe authority, admitted numerical identity, sole executable
owner, same-live P5 terminal transfer, consumed canonical commit, coherent idle/
paired frontiers, no retained-history replay/repack, conservative poison/uncertain
effects and strict supported artifact validation remain profile-scoped requirements.
Native/reference/experimental build success does not promote another execution graph.

## Performance and safety sanity

Compare matched workload/checkpoint/profile/sampler/cache state and stated timer/
memory boundaries. Historical practical throughput or no-swap observations are
not installed SLAs, proof of unlimited lifetime or new hardware coverage.
Use [performance](performance.md) and affected real operation, not a confidence
benchmark campaign after an already-closed blocker.

## Provenance

Retain exact source/payload/wheel, dependency/tokenizer/checkpoint, host/build inputs,
reference identity and receipt evidence for each selected decision. Historical paths
and hashes remain literal. Installed identity, source/build provenance and host ABI
compatibility are separate; a current environment observation cannot reseal an
unqualified numerical/native payload into approval.

## Evidence validity commands

Use existing manifest/material/receipt checks at their scope; a historical SHA check
verifies history, not current qualification. R1 material verification is not ordinary
startup. Installed inspect verifies admission but is not affected real-model acceptance.
Earlier commands and their old attestation-staleness interpretation stay in the edition.
No receipt or source-surface maintenance is requested merely to keep HEAD promotable.

## Cheap gates

Focused tests, Markdown/anchor and provenance/material checks are cheap feedback,
not release approval. Historical cargo/CMake/build commands remain evidence recipes,
not a requirement to rebuild native/runtime environments during document compilation.
Do not bypass pins, skip required semantic gates or change an immutable expected
result to make a boundary look closed.

## Explicitly unsupported/unqualified

Unsupported scope is the selected profile's documented exclusion, not a blanket
old "MTP/Vision/Web unsupported" list for today's repository. Internet/multi-user
security, cross-backend native state, distributed/crash-safe exactly-once effects
and above-qualified envelopes are not inherited by package publication or projection.
