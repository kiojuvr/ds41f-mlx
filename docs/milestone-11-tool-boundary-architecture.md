# Milestone 11 tool-call / session-boundary architecture

Status: **M11_TOOL_BOUNDARY_QUALIFIED** for Chat Completions ordinary client function tools on the official DeepSeek V4.1 Flash checkpoint.

Primary evidence: `artifacts/m11/tool-boundary-qualification.json` (`schema: ds41f.m11.tool-boundary-qualification.v1`).

## Authority model

M11 keeps the M8/M9/M10 substrate unchanged. There is still exactly one executable cache authority:

```text
idle:        M8LiveContinuationSession.live_cache (DeepseekV41Cache[40])
append:      P6/P7 DeferredPrefillAppend privately owns that cache until seal
decode:      OMLXGenerationSession / BatchGenerator / GenerationBatch owns cache
persisted:   M9 artifact is dormant storage only
```

Tool calls do **not** introduce another executable state representation. Protocol-visible tool identity is metadata derived by the official `deepseek-recipe` `StreamProcessor`.

## Tool boundary decision

The cache/token authority is frozen at the backend model boundary, not at HTTP completion and not by local DSML parsing:

```text
GenerationBatch response with finish_reason consumed
-> emitted token is appended to M8 token_history
-> OMLXGenerationSession.extract_final_state() / BatchGenerator.extract_cache
-> M8 idle cache frontier == len(all_tokens)
-> deepseek-recipe processor is finalized for protocol response metadata
```

Real evidence showed the model may complete a recipe-visible tool call and then continue generating until `max_tokens`; waiting for natural `GenerationBatch` length/stop would leave hidden post-tool tokens in cache and make the next recipe tool-result turn a non-extension. M11 therefore uses an official-parser probe: after the live `StreamProcessor` emits tool-argument evidence, a fresh official `StreamProcessor` is run over the already-consumed token prefix plus an artificial backend Stop. If official recipe output exposes a completed tool call, generation is stopped immediately and M8 extracts the scheduler cache at that already-consumed token frontier. This avoids local DSML parsing and avoids protocol-only truncation with a divergent cache underneath.

## Recipe authority

M11 uses official recipe objects for:

- request conversion and prompt encoding via existing `prepare_request()`;
- V4.1 tokenization;
- stream parsing via `StreamProcessor`;
- protocol response chunk generation and IDs.

Local code only records the already-generated protocol JSON fields (`tool_calls`, `call_id`, function name, arguments). It does not implement DSML parsing or a prompt template.

## Implemented interface

`ds41f_mlx.runtime.tool_boundary_session.M11RecipeToolSession` provides:

- `start_from_prepared(...)`: official recipe request -> DENSE_P0_P7 prefix prefill -> P5 terminal holdout -> M8 live generation;
- `run_current_assistant_turn(prepared)`: feeds tokens to official `StreamProcessor`, commits the GenerationBatch finish boundary to M8 idle cache, then returns parsed protocol tool metadata;
- `continue_from_prepared(prepared)`: exact-prefix-extension check against current `all_tokens`, append only suffix[:-1], consume suffix[-1] once, start GenerationBatch;
- `persist_idle(...)` and `restore(...)`: M9 idle persistence at tool-call boundaries.

Invalid next-turn requests are rejected by official conversion and/or M8 exact-prefix-extension before cache mutation.

## HTTP serving relationship

The existing M7 HTTP endpoints remain request-local and single-flight. M11 adds a backend-local session object suitable for a future session API/agent harness. The production serving code need not rebuild the conversation across tool-result turns once wired to this object; it can retain a session id that maps to one `M11RecipeToolSession` and route the next official recipe request through `continue_from_prepared()`.

## Qualified subset

Qualified protocol target is OpenAI Chat Completions with ordinary client function tools because it carries coherent `tool_call.id`, function name, and arguments and maps directly to subsequent `role=tool` messages. Responses and Messages use the same parser boundary but remain unqualified for M11 because their continuation/request identity semantics were not needed to prove the cache boundary.

Real observed tool call:

```json
{"name":"lookup_weather","arguments":{"city":"Paris"}}
```

The protocol call id was generated by official recipe response code (`call_<response-id>_0`) and was reused in the subsequent `role=tool` message. A deterministic stub returned `{"city":"Paris","weather":"sunny 21C","source":"m11_deterministic_stub"}`.

## Qualification closeout

The closeout runner `tools/run_m11_tool_boundary_qualification.py` proved two real-model flows:

1. uninterrupted live session: user -> parsed tool call -> deterministic tool result -> exact-prefix extension -> zero-replay continuation -> final assistant turn;
2. persisted boundary: assistant tool call committed -> M8 idle -> M9 persist -> fresh process restore -> tool result -> exact-prefix extension -> zero-replay continuation -> final assistant turn.

Recorded gates:

- tool-call frontier after early official-parser stop/extract: `321` tokens;
- next recipe prompt tokens with tool result: `363`;
- exact-prefix extension: true, suffix `42` tokens;
- prompt replay count: `0`;
- full-cache repack/reconstruction count: `0`;
- persisted artifact tensors: `280` (40 layers x 7 slots);
- cache offsets: all equal frontier at idle/restore boundaries;
- invalid wrong `tool_call_id` result: official recipe conversion failed before session mutation.

## Diagnostics

M11 session diagnostics include:

- M8 replay/repack counters;
- cache-frontier equality;
- generated tokens at each committed boundary;
- protocol finish reason;
- recipe-visible tool ids/names/arguments;
- bounded event records.

Expected invariant gates remain: prompt replay `0`, full-cache repack `0`, exact-prefix-extension true, all 40 cache offsets equal `len(all_tokens)`, no fresh-prefill fallback after tool result.
